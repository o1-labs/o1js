# berkeley vendored layout — provenance & maintenance

These files let `mina-signer` produce/verify the **berkeley** (o1js v2.9.0) zkApp
transaction format in addition to the current **Mesa** format. They are frozen
snapshots — do not "improve", reformat, or regenerate them casually.

## Source

- o1js git tag: **`v2.9.0`** (the berkeley release; published signer = `mina-signer@3.0.7`).
- Golden test vectors validating this code: generated by the real
  `mina-signer@3.0.7` and stored at `../test-vectors/berkeley.ts`. Their provenance is
  reproducible via `../test-vectors/verify-berkeley-vectors.mjs` (re-signs every vector
  with `@3.0.7` and asserts a match).

## Why this exists: the berkeley ↔ Mesa delta

A whitespace-insensitive diff between `v2.9.0` and current `HEAD` proves the
entire semantic difference is **two module-level constants**:

1. `js-layout.ts` — zkApp state arrays use `staticLength: 8` (berkeley) vs `32` (Mesa).
   Exactly 5 sites (appState ×3, account-precondition `state` ×2).
   ```
   git diff -w v2.9.0 HEAD -- src/bindings/mina-transaction/gen/v1/js-layout.ts
   # → only 5 lines: staticLength 8 → 32
   ```
2. `crypto/constants.ts` — `protocolVersions.txnVersion` is `3` (berkeley) vs `4` (Mesa).
   ```
   git diff -w v2.9.0 HEAD -- src/bindings/crypto/constants.ts
   # → only: txnVersion 3 → 4
   ```

The delta only affects a commitment through **defaulted/omitted** values:
`from-layout.ts` maps a supplied array 1:1 (ignoring `staticLength`) and only pads
to `staticLength` when the value is `undefined`. The always-signer-constructed fee
payer (`AccountUpdate.empty()`) is therefore the reliable carrier of the appState
padding delta; `txnVersion` bites when `permissions.setVerificationKey` is present.

## What is vendored (2 files) and what is reused

Only the files that actually carry the delta are vendored:

- **`js-layout.ts`** — verbatim `v2.9.0` snapshot (`staticLength: 8`).
- **`transaction-bigint.ts`** — a rewired shell of the `v2.9.0` file:
  - imports the vendored `./js-layout.js` (staticLength 8),
  - re-imports all leaf types from the **shared** current bindings,
  - overrides only `TransactionVersion` so `empty()` returns `txnVersion 3`
    (declared above `customTypes` so `SignableFromLayout` closes over it; an
    explicit `export { TransactionVersion }` shadows the star re-export).

Everything else is the **shared** current bindings, which are byte-identical to
`v2.9.0` (so reusing them is faithful, and avoids frozen duplicates):

```
git diff -w v2.9.0 HEAD -- src/bindings/lib/from-layout.ts                       # = 0 lines
git diff -w v2.9.0 HEAD -- src/bindings/lib/binable.ts                           # = 0 lines
git diff -w v2.9.0 HEAD -- src/bindings/mina-transaction/v1/transaction-leaves-bigint.ts  # = 0 lines
git diff -w v2.9.0 HEAD -- src/bindings/mina-transaction/v1/transaction-leaves.ts          # = 0 lines
git diff -w v2.9.0 HEAD -- src/bindings/mina-transaction/v1/derived-leaves.ts              # = 0 lines
git diff -w v2.9.0 HEAD -- src/bindings/mina-transaction/gen/v1/transaction-json.ts        # import reorder only, no semantic change
```

## Re-diff check (run if the shared bindings ever change)

If a future release modifies the shared `from-layout.ts`, `binable.ts`,
`transaction-leaves*.ts`, `derived-leaves.ts`, or `transaction-json.ts` in a way
that is NOT a pure reorder, the reuse assumption breaks and these vendored files
must be re-evaluated against `v2.9.0`. Re-run the six diffs above; any non-empty
(beyond import reordering) result means the berkeley path needs a real snapshot of
that file too. The golden vectors in `../test-vectors/berkeley.ts` are the
backstop: `berkeley.unit-test.ts` will fail if the berkeley output ever drifts.
